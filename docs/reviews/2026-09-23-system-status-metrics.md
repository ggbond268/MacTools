# System Status collection review

Reviewed on 2026-09-23. Scope: the System Status plugin's active dashboard, menu bar values, process list, and underlying samplers. This review checks units, counter identity, timing, aggregation, and unavailable data. Source agreement is not a claim of identical results across sampling windows or hardware.

Follow-up: the [chart choices and sampling review](2026-09-23-system-status-chart-metrics.md) generalizes chart selection and replaces unconditional family collection with consumer-driven demand. Its lifecycle policy supersedes the background process-scan intervals described in the historical measurements below: hidden process lists now stop scanning.

## Findings and changes

| Metric | Contract and conclusion |
| --- | --- |
| System CPU | Busy ticks divided by total ticks, including nice time, across the host. Fixed 32-bit counter wraparound; the result is a fraction of total CPU capacity. This differs from the process list's per-core percentage. |
| CPU load | `getloadavg` returns the one-minute load average. It is a load value, not a percentage. No conversion defect found. |
| Application processes | Retains the preceding change: group all observed members before selecting leaders; sum `ps` CPU percentages and physical footprints. An incomplete memory total is unavailable. Attribution uses bundle paths, optional responsibility information, and same-user ancestry. |
| System memory and swap | The existing used-memory formula matches Stats: active + inactive + speculative + wired + compressor - purgeable - external pages. Swap counters are already bytes. Removed the hard-coded 16 KiB page-size fallback; an unavailable page size does not produce a guessed reading. Host-port lookup is shared rather than repeatedly acquiring send rights. |
| Memory pressure | Native normal/warning/critical states remain independent of used memory. The current chart adds a separately labeled constrained-memory percentage estimate; see the [percentage definition and validation](2026-09-23-system-status-chart-metrics.md#memory-pressure-percentage). Unknown states and failed percentage reads remain independently unavailable. |
| Disk capacity | Measures the home directory's volume. Available capacity for important usage can include reclaimable storage; used capacity therefore need not equal `df` or the sum of file sizes. No arithmetic defect found. |
| Disk I/O | Bytes are cumulative per storage driver. Fixed device hot-plug/reset handling using registry identities and per-device deltas. Drivers that expose no usable statistics are skipped, as before, rather than hiding every readable drive. A changed readable-device set starts a new baseline; unavailable totals and the first baseline do not become zero. Removed the fixed 10 GB/s cutoff. |
| Network | Preserves the previous system-wide total across active physical interfaces. Multiple interfaces are labeled explicitly instead of showing a primary-interface name beside a total; the address remains the primary interface's address when available. Each interface has its own 64-bit baseline so another interface's activity cannot hide a reset. IPv6 default routes are considered; virtual/VPN interfaces are excluded to avoid duplicate traffic. Removed the fixed 2 GB/s cutoff and the 32-bit counter fallback. Routing-message parsing now continues past shorter address records instead of missing subsequent interfaces. |
| GPU | The two accepted utilization keys explicitly express percentages. Fixed fractional values such as 0.5 being interpreted as 50%. Unavailable utilization remains unavailable, and the selected GPU's name and temperature stay with its utilization. SoC temperature is no longer a GPU temperature fallback. |
| CPU power | Measures CPU energy, not whole-machine or adapter power. Fixed multi-die channels being overwritten by the last channel. Prefer an explicit package total when available, otherwise sum each CPU channel's power. A changed channel set starts a new baseline. Repeated source samples retain the last valid average for at most 60 seconds; a fresh sample with no energy increment remains a valid zero. Source intervals prevent spikes when the provider updates slowly. Advancing energy still uses collection-time differencing if optional source timing is missing or does not advance. |
| Battery | Uses a present internal battery, without mixing a UPS with AppleSmartBattery telemetry. Missing capacity is unavailable, not 0%. Charge/discharge time estimates are used only in their documented states. Signed current decoding also applies to the voltage/current fallback, and valid zero current is preserved. |
| Temperature and health | SMC/HID/registry values remain hardware-dependent sensor readings. CPU/GPU temperature is a selected or averaged sensor value, not a standardized cross-device temperature. Battery health is a capacity-ratio estimate, with a cached system-profiler fallback; it need not equal Apple's calibrated UI percentage. Adapter watts describe the adapter rating, not measured instantaneous consumption. |

Network and disk throughput now divide counter changes by monotonic elapsed time captured at collection, rather than a wall-clock date supplied before other sampling work. CPU power prefers each channel's monotonic source interval and falls back to collection timing. Counter resets, identity changes, and unavailable readings establish a new baseline instead of reporting a false zero or spike. Network and disk deltas are summed before converting to integer bytes per second, preserving the previous aggregate rounding behavior.

## Initial native memory pressure implementation

This section records the original level-only chart. The later [percentage implementation](2026-09-23-system-status-chart-metrics.md#memory-pressure-percentage) supersedes its presentation and history behavior while preserving the native-state reader.

[Issue 431](https://github.com/ggbond268/MacTools/issues/431) requests pressure as an alternative to used-memory charts. Apple's [Activity Monitor guide](https://support.apple.com/en-au/guide/activity-monitor/actmntr1004/mac) describes pressure as a combination of memory availability, swap rate, wired memory, and file caching. Used-memory percentage alone cannot reproduce it; high usage may coexist with normal pressure.

The collector reads `kern.memorystatus_vm_pressure_level` into a checked four-byte unsigned integer. Apple's [XNU implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_memorystatus_notify.c) converts its internal levels to dispatch flags before returning this sysctl: 1 means normal, 2 warning, and 4 critical. These are not the internal enum's values. The read is not restricted to root on macOS. Failed reads, unexpected sizes, and unknown flags remain unavailable, independently of whether the existing usage calculation succeeds.

The pinned Stats RAM reader above uses this same sysctl. The pinned Mole implementation runs `memory_pressure` and parses its output; MacTools avoids spawning that command or interpreting a free-memory percentage as pressure. This kernel interface supplies discrete levels, not a documented continuous percentage or the exact vertical coordinate used by Activity Monitor. The chart therefore uses three labeled levels and semantic status colors. Missing historical buckets are blank; each nonempty bucket shows its highest retained reading. Minimum and maximum show levels, and there is no average of ordinal states.

Memory's expanded widget settings provide Usage (default) and Memory Pressure. The preference persists, participates in settings backup, and controls the card and detail charts, including the menu bar detail panel. Missing or unknown preferences retain Usage. Older history records decode with no pressure value. Existing usage, swap, CPU, and process accounting are unchanged by this feature.

Collection adds one small read to the existing fast sampler, with no subprocess, event source, timer, or faster polling. Charts are bounded to 120 buckets plus a final endpoint; detailed-range refresh preparation remains off the main actor. Contiguous equal levels share one filled segment to avoid rendering seams and unnecessary drawing. Existing polling and history persistence intervals still apply: events between samples or omitted by history retention are not reconstructed. Interval peaks describe retained observations, not continuous monitoring or a claim to match every Activity Monitor transition.

The pressure, plugin, and sampler suites passed all 39 tests. After chart inspection changes, the 17 pressure/plugin tests passed again, followed by all four pressure tests after the final drawing adjustment. Coverage includes native flag mapping, unavailable history, backward-compatible preferences, settings persistence/backup, interval peaks, time-axis endpoints, and inspection of the correct interval. A read-only M1 Max probe returned normal in all 1,000 reads, agreeing with the raw value 1 and four-byte size. The read-and-classify loop averaged approximately 2.1 microseconds per call in this local Debug probe; this is not a cross-device performance guarantee. Offscreen AppKit renders checked both chart modes at 420- and 620-point widths in light and dark appearances, using synthetic transitions without inducing memory pressure on the machine.

## Validation

Focused XCTest covers CPU rollover, GPU percentage units and device association, high-throughput and reset boundaries, multi-interface totals, routing-message parsing, multi-die energy accounting, source timestamps, slow-provider reuse/expiry, legitimate zero power, battery source/state rules, and signed battery current. All 39 tests across the sampler, process aggregation, and plugin suites passed during CPU-power recovery; all 22 sampler tests passed again after setting the reuse bound to 60 seconds. Changelog validation and whitespace checks also passed.

Live read-only sampling on an M1 Max running macOS 27.0 build 26A428 confirmed available CPU usage, memory/swap, Ethernet throughput, disk activity/capacity, GPU usage, temperatures, and battery readings. The first network/disk sample correctly remained unavailable until a baseline existed. A final Debug probe observed approximately 11 ms for a warm fast sample, 142 ms for a slow sample, and 311 ms for the initial fast sample including its 200 ms CPU baseline wait. These are individual observations, not performance thresholds, and do not include the separate process scan.

On this machine, short probes initially showed unchanged CPU energy and source timestamps. A longer trace established that the provider does update intermittently: one source interval was approximately 43 seconds, yielding 5.57 W when the new energy arrived. Treating every repeated timestamp as unavailable therefore hid useful readings between updates. The final tracker preserves the latest valid average for at most 60 seconds, clearing it on a counter reset, channel change, read failure, or expiry. It does not invent a value before the first valid interval. This is a provider average, not a claim of one-second power resolution on this OS.

The recovered path produced approximately 3.42, 6.67, and 5.07 W in a continuous read-only trace. After the first valid interval, all subsequent displayed samples retained a reading, including unchanged raw samples. That cold probe waited about 46 seconds for its first update, so immediate power availability cannot be promised on this OS. Transient read failures clear the displayed cache but retain the cumulative baseline, preserving the previous recovery behavior without requiring another full provider interval.

Read-only experiments with Energy Model alone, retained subscription channels, fresh subscriptions, and macmon's broader group selection did not eliminate this intermittent behavior. [Stats](https://github.com/exelban/stats/blob/ef3146cfccc79f4993d6f6a1520b2701106a4957/Modules/Sensors/readers.swift) differences energy over elapsed collection time; [macmon](https://github.com/vladkens/macmon/blob/6919d7781b6c55a6e3bedff83a210435837e1dfe/src_lib/sources.rs) uses sample deltas and measured intervals. Neither makes a raw-element timestamp a required prerequisite for advancing energy. The compatibility path is retained here; source timing additionally avoids turning deferred updates into power spikes.

[macmon issue 76](https://github.com/vladkens/macmon/issues/76) reports a related symptom. Its [unmerged PR 77](https://github.com/vladkens/macmon/pull/77) limits an SMC fallback to validated M3 Max rails. That mapping is not applied to this M1 Max. The Stats CPU-package SMC keys were unavailable locally, while whole-system/SoC keys were readable; substituting those would change the metric's meaning. The live probes are not a hardware compatibility matrix; Intel, Ultra, and external-GPU behavior remains unverified on physical devices.

## Follow-up regression and performance review

The follow-up review corrected overly broad changes from the initial audit: selecting only the primary network interface would omit concurrent traffic, rejecting every zero-energy delta would hide fresh zero readings, rejecting every repeated timestamp would hide slow-provider readings, and rejecting every disk when one driver lacks statistics would discard unrelated valid data. The final implementation retains aggregate physical traffic, bounded reuse of valid CPU power, and independent readable-disk collection. CPU, memory, disk-capacity, battery-health, and process-CPU definitions otherwise retain their established scope, with the previously requested application grouping and footprint-based process memory.

A temporary probe compiled the original committed sampler and the working sampler into the same executable. It compared 300 normal-input results across CPU usage, network/disk rates, CPU power, GPU percentages, and battery power; all agreed. These checks deliberately exclude the documented bug boundaries and requested accounting changes. Adjacent live memory readings also matched exactly in that run.

The same read-only Debug probe observed the following wall-clock durations on this Mac. Fast sampling used five repetitions, and slow/process sampling used three. These observations establish no benchmark guarantee and do not measure renderer frame times.

| Collection | Original | Working version |
| --- | --- | --- |
| Warm fast metrics | 4.8-9.1 ms | 5.0-8.6 ms |
| First slow metrics | 164 ms | 166 ms |
| Cached slow metrics | 11.8-12.7 ms | 10.4-10.9 ms |
| Process scan | 91.9-97.9 ms | 99.3-101.6 ms |

Process aggregation adds native identity/footprint queries and is slightly more expensive per scan. It remains outside the main actor, coalesces concurrent scans, and runs every three seconds only in foreground mode, with a five-minute background interval. Normal fast collection adds no subprocesses or additional polling loop. Temperature, network metadata, and fallback battery-health caching remain in place.

## Independent CPU and resource review

A further source review retained the existing CPU formulas. Apple's [Recount documentation](https://github.com/apple-oss-distributions/xnu/blob/main/doc/observability/recount.md) distinguishes time counters from energy counters. The [processor implementation](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/processor.c) supplies user, system, and idle ticks to the host aggregate; Stats uses the same busy/total host ratio. CPU utilization is CPU time occupancy, not a frequency-weighted performance score or a power estimate. Apple's [ps implementation](https://github.com/apple-oss-distributions/adv_cmds/blob/main/ps/tasks.c) sums thread CPU usage and [formats it](https://github.com/apple-oss-distributions/adv_cmds/blob/main/ps/print.c) with `TH_USAGE_SCALE`. Its recent kernel window is not the same as the dashboard's between-poll host window. Application totals can exceed 100% and should not be expected to equal the host percentage.

Mole's parked-core adjustment is specifically a per-core wall-time normalization. In a local three-window native probe, aggregate tick time varied between approximately 0.75 and 1.17 times the individual wall-time capacity, but covered approximately the full capacity over the combined window. Applying a wall-time floor to each host sample would treat deferred counter updates asymmetrically. There was no evidence here to replace the established host ratio with that heuristic. This observation does not establish parked-core behavior on every OS or processor.

The concrete additional defect was missing cleanup of IOReport subscriptions and dynamic library handles. The reader now releases its retained CF subscription before closing the library; symbol-loading failures also close their handle. This follows [macmon's IOReport destructor](https://github.com/vladkens/macmon/blob/6919d7781b6c55a6e3bedff83a210435837e1dfe/src_lib/sources.rs). A temporary native lifecycle probe created and destroyed readers in four batches of ten: live Mach port counts previously grew through 29, 39, 49, and 59, but remained 19 in every batch after the fix. This affects collector destruction/recreation, not every sample from a long-lived reader. The final sampler suite passed all 22 tests with no failures or runtime warnings.

A separate read-only probe measured ten warm polling cycles per mode, sleeping three seconds after each cycle, using the final Debug collector. `getrusage` measured both the probe and its reaped child processes; the foreground mode requested 20 ranked entries and included slow metrics every fifth cycle. No synthetic CPU load or process fan-out was created. Initial hardware discovery, UI rendering, application-name/icon resolution, and history persistence were outside this measurement.

| Warm sampling mode | Observed duration | Collector CPU time | Child CPU time | Average CPU, one core = 100% |
| --- | --- | --- | --- | --- |
| Fast menu bar metrics | 31.23 s | 99.9 ms | 0 ms | 0.32% |
| Foreground with process scans | 33.21 s | 669.5 ms | 614.0 ms | 3.86% |

Foreground process scans took approximately 107-120 ms each. The process path dominates collection cost; the fast path launches no commands during these warm cycles. A preceding run observed 0.33% and 3.87%, respectively. These are local Debug observations, not whole-app CPU or battery-life measurements. Background mode retains 30-second fast sampling and five-minute process sampling. No additional timer, more frequent scan, or new subprocess was introduced by this review. CPU watts remain a sensor-window average with bounded reuse, separate from Activity Monitor's relative Energy Impact score; the review does not establish instantaneous watts or power-meter accuracy across hardware.
